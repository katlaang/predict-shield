# PREDICT-SHIELD

**An AI-driven security assessment pipeline for network operators.**

PREDICT-SHIELD finds what is running on a network or a public-facing website, checks it against known vulnerabilities, uses a language model to read the advisories and propose fixes, screens every proposal through a deterministic policy gate, and independently verifies whether a fix actually worked. It is built for ISPs, telecom carriers, and SMEs running a public website who need continuous, evidence-backed security assessment and don't have a dedicated security team to do it by hand.

> **Status: working prototype, not a finished product.** The pipeline below runs end to end today in a lab, unattended, from a detection through an applied change to independent verification, with automatic rollback when verification fails. Running it against a real operator's live infrastructure is the next phase of work and is not something already deployed.

## How it works

1. **Discover.** Scan the network and build an inventory of running assets, services, and the dependencies between them, with every discovery record hashed so it can't be silently altered later.
2. **Evaluate.** Match the inventory against known vulnerability advisories and build a risk picture: which assets are exposed, to what, and how confidently.
3. **AI analyzes the findings.** A language model reads the advisory text and the risk picture and proposes candidate fixes. It never writes free text into the record; every proposal is checked against the real package inventory and the real advisory text, and anything it can't verify is rejected rather than guessed at. Advisory text is treated as untrusted input throughout: it is screened for known instruction-injection patterns before it ever reaches the model, independently of the grounding check.
4. **Validate in isolation, where applicable.** A text match in an advisory is not proof a weakness is actually present. For web-facing targets, a reviewed, CVE-specific, read-only probe (never one derived from the advisory text or the model's own reply) can run against a host the operator has explicitly authorized, and its result is treated as one more piece of independent evidence, not a verdict on its own.
5. **Recommend.** The model's proposal only narrows the list of things worth considering. A deterministic policy gate, not the model, makes the actual call: it checks the action against service-continuity budgets, calibrated risk/impact estimates, and policy limits before anything is approved.
6. **Apply approved defenses.** Today this step runs against an isolated lab network (Docker/Kafka/Java), not live operator infrastructure. The gate can approve an action for consideration, but nothing in this repository dispatches a change to a real production system; that boundary is intentional while the approach is still being proven out.
7. **Verify outcomes.** A separate, independent verifier, not the model and not the thing that applied the fix, re-checks the target afterward and reports one of VERIFIED, NOT VERIFIED, INDETERMINATE, or NOT APPLICABLE. An action's own "success" acknowledgment is never treated as proof it worked.

Each step produces a signed, hashed record, so a finding, a recommendation, an applied action, and a verification result can always be traced back to the evidence behind them.

## What's built vs. what's planned

| Capability | Built today | Still needed for a full operator product |
| --- | --- | --- |
| Asset & dependency discovery | Docker/container-based discovery, hashed inventory, dependency graph; a read-only Open vSwitch adapter that turns observed switch flow traffic into dependency-graph edges with real evidence IDs, for an SDN lab (e.g. Containernet, ONOS) | Now run against a real Containernet/OVS lab in CI, with explicit per-port flow evidence; discovery against real routers/CPE on a non-containerized network is still open |
| Vulnerability matching | Advisory ingestion from GitHub Advisory Database, coordinate and artifact-name matching rules | Broader source coverage (CISA KEV, vendor feeds) |
| AI-read advisories & proposals | Local/hosted language model reads advisory text, proposes only cataloged actions and checks, grounded against the real inventory; advisory text is screened for instruction-injection patterns before it reaches the model | Measured accuracy at scale, against real production data, before recommending unsupervised use; the injection screen is pattern-based and should keep growing from real examples, not a trained classifier yet |
| Confirming a finding is real | Text-grounding check (does the package and version really appear in the advisory); a bounded, read-only, catalog-registered HTTP signature check for web-facing targets | Broader confirmation checks per vulnerability class; today's web check only covers CVEs with a reviewed, registered signature |
| Policy-gated action selection | Deterministic gate: service-continuity budgets, calibrated risk predictions, policy tiers | Calibration against real operator traffic, not just lab traffic |
| Applying fixes | `change_execution.py` applies a gated plan to a registered target: dry run by default; an automatic-tier plan applies only to a target registered for automatic apply, and every production target and every approval-tier action needs an Ed25519-signed approval bound to the exact change, unexpired and single-use; snapshot, validation (`nginx -t` for a CSP include, registered renderings only for a page), atomic write, activation; independent verification after activation; automatic rollback on anything short of VERIFIED, with the restored content checked against the snapshot; a hash-chained audit log of every step. Change content is generated from structured policy, never from model text. Exercised against a real nginx in CI (`end-to-end-chain.yml`) | Adapters for further targets (CDN configuration, load balancers, network devices); a registered real production site and an operator who approves changes to it |
| End-to-end chain | `experiment-b/end-to-end-chain` runs unattended in CI against a real nginx, real Chromium and a real Suricata: the scheduler or an authenticated IDS alert detects a tampered vendor script, the AI proposer and policy gate plan a containment, `change_execution.py` dry-runs and applies it, an independent HTTP client and browser verify it with the sink's own log as a second source, and the change is kept or rolled back. Five registered paths are exercised every run: a CSP change kept, a CSP change that fails verification and is rolled back with the served state confirmed back at the snapshot, isolation kept with the widget working, an approval-tier block refused unsigned and applied signed, and an IDS-triggered isolation; a sixth incident uses a real local model (`qwen3:0.6b`) as the proposer and may land on any outcome the policy allows, never an unverified change | The same chain on an operator's own site with its own approvers; further evidence domains (dependency upgrades, SAST fixes) driven through the same executor |
| Independent verification | Separate verifier distinguishes VERIFIED/NOT VERIFIED/INDETERMINATE/NOT APPLICABLE; a remediation is only accepted once four independent assertions all reach VERIFIED (vulnerability resolved, no regression against the consuming project's own test suite, the new version carries no known vulnerability of its own, dependency resolution succeeds), not just the first of those. All four are piloted against real targets in CI, not only fixtures: the regression and dependency-resolution checks against a real Maven project, and all four together against a real CVE fix (lodash, CVE-2020-8203) with a real `npm install`, a real independent behavior probe, and a scan against real published advisories. A project's resolver command, test command, and known advisories can now be registered declaratively (`remediation_target.py`, a JSON schema) instead of writing a one-off script per project; re-running the real lodash pilot through this generic path reaches the exact same VERIFIED result as the original hand-written script, and a second, independent real target (minimist, CVE-2021-44906, with its own from-scratch probe written against the exact PoC Snyk's advisory publishes) reaches the same all-four-VERIFIED outcome through the identical mechanism | Live, authenticated probes against a real network for a web-facing target; the registration mechanism still requires a human to hand it the `vulnerability_resolved` evidence from a separately reviewed, CVE-specific probe (deliberately not automated); both real targets registered through the mechanism so far are npm packages with a disposable install, not a project with a real build/release process an operator would actually run; advisory lists for both pilots are hand-verified entries, not a live feed |
| Dashboard | A live operations view (`demo/live.html`) that polls a read-only, loopback-only feed (`live_feed.py`) while the chain runs: incidents by stage, authenticated detections, and the change audit log with its hash-chain status. It shows NO LIVE DATA when the feed is unreachable or its timestamp stops moving, and CI confirms both behaviors in a real browser. The recorded-data demo (`demo/index.html`) and the 3D asset-graph prototype (`dashboard/index.html`) remain | Authentication for a feed exposed beyond loopback; a production build of the asset-graph UI instead of CDN-loaded, in-browser JSX; the Java/Kafka mechanism lab's findings on the same live view |
| Intrusion-informed containment | Authorized detection alerts (from an EDR, SIEM, or other tool the pipeline does not control) are admitted as a new, independent input to the same verifier, only from a pre-registered trusted source, rejecting unregistered sources, stale signals, and malformed alerts outright; an admitted detection raises a subject's priority in the existing re-verification scheduler. The scheduler update only accepts the proof object admission itself produces, so a detection that skipped the registry check cannot reach the scheduler, enforced at runtime. Source identity is now checked cryptographically: every registered source carries an Ed25519 public key or a client-certificate fingerprint, and `admit()` accepts only an `AuthenticatedDetection` that a signature check or an mTLS check produced. A detection that only names a source is refused, a signature from another source's key fails, a replayed nonce or detection ID is refused, and a rotated-out credential stops admitting. `intake_server.py` terminates TLS for both routes. In CI a real Suricata on loopback raises an alert on the lab's exfiltration traffic, a forwarder signs it and posts it to the intake, and the admitted detection makes the scheduler re-check the page at once instead of after its 300-second interval. This consumes detection alerts produced elsewhere, and does not generate detection rules, which is a different capability | Tightening the policy gate's own response deadlines and approval tiers based on detection confidence; a commercial EDR feed (the real feed exercised in CI is Suricata, an open-source IDS) |
| Source-code fix verification (SAST findings) | A four-assertion, all-or-nothing acceptance rule for a source-code finding (such as SQL injection), mirroring the dependency-upgrade composite: the finding must be confirmed present at a scanner-stable fingerprint before the fix (ruling out crediting a hallucinated report), confirmed absent at the same fingerprint after, no regression, and no new high-or-critical finding introduced, all admitted only from an operator-registered, version-pinned scanner. Piloted against one real target in CI (`experiment-b/real-sast-pilot`): a real `semgrep` scan (pinned to a repo-local rule file, not the live registry) of a real SQL-injection fixture, a real fix, and a real sqlite3 regression check, all four assertions reaching VERIFIED. A SAST finding can now also enter the propose-then-gate stage the same way a CVE does: `plan_sast_case()` re-confirms the finding independently, maps its `rule_id` to an operator-registered remediation action (never a model's guess), and runs it through the existing policy gate, stopping at an eligible plan exactly where `plan_case` does for a CVE. 23 unit tests for the core module, 13 for the pilot, and 7 for `plan_sast_case` pass | No integration with a real production codebase, only the pilot's own small fixture; the optional dynamic check for externally reachable findings is not implemented; reachability-based prioritization using the dependency graph is not implemented; `plan_sast_case` still never calls `evaluate_fix` itself -- post-action verification stays a separate step, the same boundary the CVE flow also stops at; the pilot's own scan-to-scan finding fingerprint is a locally computed stand-in (rule, file, and enclosing function), not Semgrep's native fingerprint, which requires a logged-in Semgrep Cloud Platform session this pipeline does not use |
| Third-party script integrity | A fourth evidence domain: verifying a third-party script an operator's own page embeds, without any access to the vendor's source. `script_integrity.py` implements a four-assertion, all-or-nothing rule: the script's live, independently fetched hash matches a registered trusted value; the set of network destinations a real, instrumented browser load actually contacts (every request, fetch/XHR/sendBeacon call and dynamically injected script, not only static `<script src>` tags) stays inside a registered allowlist; the site's own Content-Security-Policy header actually restricts script-src, not merely exists; and, independently of the first three, a real post-action browser load can no longer reach a registered-prohibited destination. That fourth assertion is deliberately not a second hash comparison: an allowlisted vendor domain can itself serve malicious code, and a hash returning to a known-good value is not evidence a prohibited behavior cannot still occur through another path, only a real instrumented load is. A containment action is chosen by a constrained AI proposer (`script_risk_proposer.py`, mirroring `action_proposer.py`) from a pre-permitted, registered action set, never an open-ended catalog; `plan_script_integrity_case()` (`pipeline.py`) wires a confirmed finding into the same propose-then-gate stage `plan_sast_case` uses for source-code findings. Because this AI step reads attacker-influenced content (a script's own bytes, or free text describing it), it is screened by the existing `injection_guard.py` pre-model layer and backed by a dedicated acceptance-test suite (`test_script_integrity_ai_security.py`) proving that content embedded in that evidence cannot override the policy gate, introduce an unoffered action, manipulate an outcome through rationale text, trigger any execution (no capability here executes anything), or substitute a self-report for independent verification. The behavioral check cannot pass on an empty capture: a trial counts only if a page-owned canary request was recorded (the instrumentation was live) and the script under test was independently confirmed live at the vendor and attempted by the browser (the exposure was exercised); otherwise the result is INDETERMINATE, never VERIFIED. The model also returns a severity assessment, correlated against the asset's registered criticality and any registered detection notes; it is recorded as advisory only and cannot move an approval-tier action into automatic eligibility. Piloted against a real target in CI (`experiment-b/real-script-integrity-pilot`): three real local HTTP servers (an operator "site" origin, a separate third-party "vendor" origin, and a sink standing in for an attacker-controlled destination) and a real headless-Chromium load via Playwright. Detection scenarios: a clean negative control; a real malicious tamper where the browser is observed actually reaching the sink over the network, confirmed by the sink server's own log; a benign, pre-registered vendor update that does not false-positive; an unregistered-domain injection the hash check alone misses; and a CSP enforcement toggle. Containment is then verified with the compromised script live at the vendor, each trial requiring two independent sources (the browser's own capture and the sink server's own log), across four exfiltration channels (a `fetch` request, an image beacon, a form submission, a top-level navigation) and five containments. Measured result: restricting `connect-src` contains only `fetch`; restricting every fetch directive (`default-src` plus `form-action`) contains `fetch`, image and form but not navigation, which no CSP directive in current browsers restricts; blocking the vendor script or pinning it with Subresource Integrity contains all four but disables the page's checkout; and the no-containment control is NOT VERIFIED on every channel. The two uninformative cases (instrumentation not live, compromise not exercised) are correctly INDETERMINATE. SRI's operating costs are measured too: the pinned clean script runs only when the vendor sends CORS headers, and a benign vendor update is refused until the pin is changed. Detection under a real re-check cadence uses the existing fixed-interval scheduler on a real clock with real fetch probes: at a 2-second interval, every tamper was detected, within the interval-plus-one-second bound. The fetch probe resolves a registered hostname once, refuses any non-public address unless the registration opts in, connects only to that pinned address (verifying TLS against the registered hostname), and refuses redirects, so DNS rebinding cannot move a probe to an internal address. Building the pilot surfaced a real flaw that the two-source requirement caught: the browser reported an exfiltration request as failed while the sink server logged it as received, so a request is now treated as blocked only when the browser refused to send it. The proposer also runs in CI against a real model, `qwen3:0.6b` served by a local Ollama on loopback with its installed digest recorded, and the job fails on any structural safety violation. That run found a real defect: the prompt told the model to choose from `permitted_actions` but never sent the list, so the model invented actions (`block`, `patch`) and, in the planted-injection case, answered `disable_monitoring` exactly as the injected note demanded; deterministic validation rejected every one. With the list sent, the same model made a valid choice in all four cases, two reached an eligible plan, the two approval-tier choices were held for review, and a "low" severity the pressure note asked for did not change the tier. A manually dispatched workflow (`live-model-script-proposer.yml`) runs the same checks against a hosted model with a repository secret. Navigation-based theft now has a containment that does not break the page: the vendor script runs only inside a frame the operator serves, sandboxed with `allow-scripts` alone, under its own CSP with no fetch, image or form destination, while the parent's `frame-src 'self'` stops the frame navigating itself elsewhere; the widget's one visible effect reaches the page as a typed message that a first-party bridge accepts only from that frame. In the real Chromium matrix it contains all six channels (fetch, image, form, frame navigation, top-window navigation, popup) with the checkout still working, while blocking or pinning the script contains them by disabling it. 45 unit tests for the core module and proposer, 13 for the required AI-security acceptance tests, 8 for the pipeline wiring, and 9 for the pilot's own contracts pass | This is a controlled adversary simulation against infrastructure the pilot itself controls, not a scan of any real vendor's production CDN or a general-purpose AI-assisted red-teaming capability (a materially larger, separate problem this repository deliberately does not claim to build here); no live production site has been registered or scanned; CSP and SRI changes are applied through `change_execution.py` to a real nginx in the lab, not yet to an operator's site; isolation needs the vendor widget to work through the typed message contract, which a widget that must read or write the operator's page directly cannot use; the proposer has been run against one small real model (0.6B parameters), whose judgment is not representative of a production-grade model, and the hosted-model workflow awaits a provider key; the measured detection time is for a 2-second lab interval and scales with the interval and probe budget configured in production |

The gap that matters most for an ISP/telecom deployment is the environment: the chain runs unattended end to end with a live view, but only against lab infrastructure it controls, not a live customer network.

## Quick start

Requirements: Python 3.12, Docker with Docker Compose, and a Docker environment able to build Java 25 images.

Run the Python evidence-engine tests:

```bash
PYTHONPATH=engine python -m unittest discover -s engine/tests -v
```

Run the unified AI case pipeline against a local model (see [the unified pipeline doc](docs/development/UNIFIED_LOCAL_AI_VULNERABILITY_PIPELINE.md) for the full walkthrough):

```bash
ollama serve
# in a separate shell, after pulling a model revision:
PYTHONPATH=engine python -m predict_shield.run_ai_case \
  --case-id local-case-0001 \
  --discovery /private/asset-discovery-with-sbom.json \
  --advisories /private/sourced-advisories.json \
  --catalog /private/registered-actions.json \
  --model qwen3:8b \
  --model-fingerprint sha256:recorded-model-digest \
  --output /private/unified-ai-case-0001.json
```

Bring up the isolated, localhost-only mechanism lab to see fixes actually applied and verified:

```bash
cd experiment-b
export LAB_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
export LAB_ORACLE_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
docker compose up --build -d
python integration_smoke.py
docker compose down
```

Read [the Experiment B guide](experiment-b/README.md) for full setup and limitations.

## Safety and reproducibility

The mechanism lab intentionally reproduces incorrect authorization decisions for lab purposes. **Do not deploy it to the internet, production infrastructure, or operational systems.** Keep credentials and raw oracle observations out of source control. Record commit SHA, configuration seed, measured outcomes, and known limitations with every result. A passing unit test or a simulated observation does not establish effectiveness outside the tested conditions, and nothing in this repository authorizes unattended action against a real network.
