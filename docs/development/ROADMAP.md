# PREDICT-SHIELD engineering roadmap

**Updated November 19, 2026.**

## AI detection scientific checkpoint (November 19, 2026)

- The completed [real local-model evaluation](https://github.com/katlaang/predict-shield/actions/runs/44470495011) used `qwen3:4b` and reported **0 accepted AI-generated rules and 0/33 detections** across 130,176 selected attack-scenario telemetry events. All five model outputs were malformed JSON containing an echoed, truncated event summary. The CI audit passed **report consistency**, not detection accuracy.
- The historical negative report is retained in [evidence](../evidence/REAL_AI_RULE_SUGGESTION_NEGATIVE_RESULT_2026_11_19.md). The rule-generation prompt has been compacted and constrained to Ollama's JSON-schema output, but a fresh performance claim requires a new, independently held-out population, properly labeled benign recordings, and real precision/recall and false-alert denominators.
- For electric-grid OT, the simulated grid policy gate now protects the real isolated Open vSwitch ICMP test. Independently probed network containment is **not** a coupled electrical-resilience test. Actual AI action choice, authenticated utility authority, and coupled power/communications behavior remain pending.
- For policy-authority outages, four physical-lab interventions and dual-principal direct HTTP probes now have conservative UNKNOWN bounds; they do not establish full current-policy verification or complete v3.1 decision utility. Issue #36 remains open.
- Historical protocol tag issue #41 remains unresolved: the pinned commit and blob were verified, but GitHub rejected automatic tag creation because the connected GitHub App lacks workflow permission. Historical commits were not modified.

## Infrastructure validation checkpoint

- **External U.S. infrastructure validation is prepared but not conducted (PR #52).** The sector-independent operator-study protocol and fail-closed evidence manifest check demand real operator permission, independent assessor evidence, and actual exposure, downtime, legitimate-request failure and false-assurance counts. Structural completeness cannot authenticate a real operator or prove impact.
- **Authority-outage action inference remains limited.** PRs #43–#50 established physical outage witnesses, four action interventions, real timed observations and conservative UNKNOWN intervals. No field critical-infrastructure resilience improvement has been quantified.
- **Evidence levels stay separate.** Software CI success, completed laboratory actions, and independent operator field impact are different evidence levels. Neither GitHub traffic nor self-reported records can bridge those levels.

 Pre-alpha. A merged implementation or passing CI proves only the documented local or CI behavior, not commercial adoption or critical-infrastructure field validation.

| Post-fix safety verification ("did the fix actually work, safely") | `remediation_verification.py` requires four assertions to each independently reach VERIFIED before a remediation is accepted, not just the vulnerability-resolved check that existed before: vulnerability resolved, no regression, no new known vulnerability in the version moved to, dependency resolution succeeds. Every check follows the same fail-closed pattern as the rest of the pipeline: a probe that cannot run is reported as unverified, never as a pass. All four are now piloted against real targets, not just fixtures, in two places: `experiment-b/mechanism-lab/verify_remediation.py` runs `mvn dependency:resolve` and `mvn test` for real against the actual Maven project built in CI (no regression, dependency resolution); `experiment-b/real-cve-remediation/verify_remediation.py` runs all four together against the one real, independently-probed CVE fix this repository already has (CVE-2020-8203, lodash 4.17.11 to 4.17.21 via real `npm install`): the existing behavior probe for vulnerability-resolved, a real `npm install --dry-run` for dependency resolution, the probe piped through a real exit-code check for regression, and a scan against two real published advisories (version ranges confirmed against OSV.dev, not guessed) for no-new-known-vulnerability. Negative-control checked: scanning the pre-fix version against those same advisories correctly flags it, confirming the scan discriminates rather than passing everything. The registration step itself is now generalized: `remediation_target.py` reads a declarative JSON schema (resolver command, test command, package/new-version/advisories) instead of requiring a new hand-written script per project, and `experiment-b/real-cve-remediation/verify_remediation_via_registration.py` re-runs the real lodash pilot through this generic path, reaching the identical `accepted: True` / all-four-VERIFIED result as the original hand-written `verify_remediation.py`, proving the generalization is load-bearing rather than cosmetic. A second, genuinely independent target was then registered the same way: `experiment-b/real-minimist-remediation/` pilots minimist's real CVE-2021-44906 (GHSA-xvch-5gv4-984h) fix, with its own `independent_probe.js` written from scratch (not reused from the lodash pilot) against the exact proof-of-concept Snyk's advisory SNYK-JS-MINIMIST-2429795 publishes (`--_.constructor.constructor.prototype.foo bar`, not the more commonly guessed `--__proto__.y`, which this version already blocks and would have silently produced a negative control that never actually exercised the vulnerability). All four assertions reach VERIFIED there too, with the same negative-control discipline (the pre-fix install must actually be observed as vulnerable before the fix is credited). 10 unit tests for `remediation_target.py` plus 2 for the minimist pilot's negative control pass | The `vulnerability_resolved` assertion is deliberately excluded from what the registration mechanism automates: it still requires a human to supply Evidence from a separately reviewed, CVE-specific probe, by design, so an operator cannot yet point this at an arbitrary project and get a fully automated verdict; both targets registered through the generic path so far are disposable npm installs, not a project with a real build/release process an operator would actually run; both pilots' advisory lists are hand-picked, hand-verified entries, not a live lookup against a real advisory feed |
| End-to-end chain and safe apply | `change_execution.py` (signed approvals, dry run by default, `nginx -t`, atomic write, verification, automatic rollback, hash-chained audit log) and `experiment-b/end-to-end-chain` run unattended in CI from detection to a kept or rolled-back change against real nginx, Chromium and Suricata, with the live view (`live_feed.py`, `demo/live.html`) checked in a real browser | An operator's own site, approvers and further target adapters |
| Public test sources | OTRF telemetry, cdnjs/jsDelivr files, OSV.dev, ET Open, DVWA and real lodash releases run weekly in CI (`public-sources.yml`), each through the same intake, executor and verifiers | A live endpoint or SIEM feed; better endpoint rules (2 of 5 held-out attacks detected today), measured on a fresh held-out set |
| Intrusion-informed containment (authorized detections as a new input) | `detection_intake.py` admits a detection alert only from a pre-registered, trusted source, following the same fail-closed registered-source pattern as `exploit_confirmation.py`; rejects unregistered sources, malformed alerts, future-dated or stale signals outright; feeds an admitted detection into the existing `assessment.assess()` pipeline as one independent evidence source and reuses the existing re-verification scheduler (marks the subject changed, raises its risk floor) rather than building a second one. The scheduler update takes the `AdmissionResult` `admit()` returns, not a raw detection, and raises `TypeError` on anything else, so a detection that skipped admission cannot reach the scheduler by construction. 15 unit tests pass; this consumes detections produced elsewhere and does not generate detection rules, which is a different, unbuilt capability | Does not yet tighten the action gate's response deadlines or approval tier based on detection confidence; the real feed in CI is Suricata, not a commercial EDR. Source identity is verified: Ed25519 signatures or mTLS client certificates against registered credentials, with replay protection, through `intake_server.py`, and a real Suricata alert drives the end-to-end chain in CI |
| Third-party script integrity (a fourth evidence domain, with no access to vendor source) | `script_integrity.py` implements the same four-assertion, all-or-nothing composite pattern for a script an operator's own page embeds: a live independently fetched hash against a registered trusted value; a real browser's own network destinations against a registered allowlist (catching a script that loads or exfiltrates through a request, not only a static `<script src>` tag); whether the site's CSP header actually restricts script-src; and, independently of the other three, whether a real post-action browser load can still reach a registered-prohibited destination -- the behavioral check a hash comparison cannot replace, since an allowlisted domain can itself serve malicious code. A constrained AI proposer (`script_risk_proposer.py`) chooses a containment action only from a pre-permitted, registered set, re-validated the same way `action_proposer.py` validates a CVE-path proposal; `plan_script_integrity_case()` wires a confirmed finding into the propose-then-gate stage. Backed by a required AI-security acceptance-test suite (`test_script_integrity_ai_security.py`) proving attacker-influenced evidence content cannot override the gate, introduce an unoffered action, or substitute a self-report for independent verification. The behavioral check refuses to pass on an empty capture: it requires a recorded page-owned canary (live instrumentation) and an independently confirmed, browser-attempted exposure, and otherwise reports INDETERMINATE. Piloted in CI (`experiment-b/real-script-integrity-pilot`) against real local site, vendor and sink servers and a real headless-Chromium load: detection scenarios (negative control, real malicious tamper reaching the sink, benign pre-registered update without a false positive, unregistered-domain injection, CSP toggle); then a containment matrix of four exfiltration channels (fetch, image beacon, form, navigation) against five containments, each trial with the compromise live and two independent sources required (browser capture and sink server log). `connect-src` contains fetch only; restricting every fetch directive contains fetch, image and form but not navigation; blocking or SRI-pinning the script contains all four at the cost of the checkout; the no-containment control is NOT VERIFIED throughout; dead-instrumentation and unexercised-exposure controls are INDETERMINATE. SRI's costs are measured (needs vendor CORS; refuses a benign update until re-pinned), detection is measured under the real fixed-interval scheduler (every tamper caught within interval plus one second at a 2-second interval), and the fetch probe pins its resolved address against DNS rebinding and refuses non-public addresses by default. The proposer runs in CI against a real local model (`qwen3:0.6b` via Ollama); that run exposed and led to fixing a prompt that never showed the model the offered actions. 75 unit and pilot-contract tests pass | This is a controlled adversary simulation against self-controlled lab infrastructure, not a scan of a real vendor's production CDN; general-purpose AI-assisted red-teaming (autonomous attack-path generation across arbitrary infrastructure) is explicitly out of scope and deferred as its own, separate capability if pursued; CSP and SRI changes are applied by `change_execution.py` to a real nginx in the lab, not yet to an operator's site; navigation exfiltration is contained without breaking the widget by sandboxed-frame isolation, which requires the widget to work through a typed message contract; the proposer has been run against one small real model only, and the hosted-model workflow awaits a provider key; no real production site has been registered |
| Source-code fix verification (SAST findings as a new evidence source) | `sast_findings.py` implements the Section 7.1 design sketch's four-assertion composite for a source-code finding: the finding is confirmed present at a scanner-stable fingerprint before the fix, confirmed absent at the same fingerprint after, no regression (reusing `regression_check.py` rather than a second mechanism), and no new high-or-critical finding introduced in the touched files, all admitted only from an operator-registered, version-pinned scanner via the same fail-closed registration pattern as `detection_intake.py`. `evaluate_fix()` mirrors `remediation_verification.evaluate()`'s all-four-or-nothing rule exactly. Now piloted against a real scanner, not only fixtures: `experiment-b/real-sast-pilot/` runs a real `semgrep` subprocess (pinned to a repo-local rule file rather than the live registry, so the scan stays reproducible without a network dependency) against a real SQL-injection fixture, applies a real fix in place, and runs a real sqlite3-backed regression check; all four assertions reach VERIFIED. The pilot's own build surfaced and fixed two real bugs along the way: `confirm_no_new_high_severity`'s severity check was comparing Semgrep's actual `ERROR`/`WARNING`/`INFO` vocabulary against a `"high"`/`"critical"` string match that could never be true (a silently vacuous check), fixed with an explicit severity map; and the before/after scans were originally run against two separately named fixture files, which (since the fingerprint includes the file's own name) made the "same fingerprint, now resolved" check meaningless by construction, fixed by scanning both states at one shared disposable path to simulate a real in-place edit. 23 unit tests for the core module plus 13 for the pilot pass, and the pilot runs in its own CI workflow (`real-sast-pilot.yml`). A SAST finding can now also be proposed and policy-gated, not only post-action-verified: `plan_sast_case()` (`engine/predict_shield/pipeline.py`) independently re-confirms the finding via `confirm_before_fix`, maps its `rule_id` to an operator-registered action (`rule_to_action`, never a model's guess at the right fix, the same discipline the CVE flow's action catalog already follows), and runs the existing `select_action` policy gate -- the SAST-finding counterpart to `plan_case`'s CVE path, stopping at the exact same propose-then-gate boundary. 7 unit tests pass | The pilot is one hand-registered fixture, not a mechanism an operator can point at an arbitrary codebase; no real scanner integration exists for a production repository; the design sketch's optional dynamic check for externally reachable findings is not implemented; reachability-based prioritization using the dependency graph in place of CVE/EPSS scoring is not implemented; `plan_sast_case` never calls `evaluate_fix` -- post-action verification stays separate, exactly as it does for `plan_case`'s CVE path too, so neither capability is actually chained end to end from proposal through applied-and-verified fix; the pilot's finding identity is a locally computed stand-in (rule, file, enclosing function via AST), not Semgrep's own native fingerprint, which requires a logged-in Semgrep Cloud Platform session this pipeline deliberately avoids |

## Reporting rules

Use precise denominators and versioned sources, distinguish physical observation from plan generation, and do not treat passing unit tests as outcome validation. Preserve negative results and report calibrated uncertainty, temporal leakage checks, action eligibility, and independent verification boundaries.
