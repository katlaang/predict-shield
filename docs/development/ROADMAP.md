# PREDICT-SHIELD engineering roadmap

**As of November 14, 2026.**

## AI decision value and infrastructure effectiveness: evidence checkpoint

The framework design scopes its one core AI-versus-deterministic question narrowly, to the continuous-assurance re-verification scheduler (a learned drift model versus the transparent priority function, under an equal probe budget); that specific comparison has not been run yet. The action-effectiveness item below is a separate, exploratory engineering study, not a precondition of the framework's value: the deterministic policy gate and verifier make every real decision regardless of how that exploratory model performs. CVE threat-ranking and advisory-reading model comparisons are deferred pending a study against real production data, and are not tracked in this roadmap for now.

- **Action-effectiveness AI comparison code is now implemented (PR #51), not empirically demonstrated.** A physical-data trainer requires a complete 1,200-action four-stream lab dataset. Once data exist, its evaluation selects the strongest eligible non-AI comparator on calibration configurations, tests a random-forest selector on 20 separate held-out configuration groups, and requires group-paired bootstrap evidence of at least 10% regret improvement against all seven predeclared deterministic comparators under a Bonferroni safeguard. Current synthetic tests confirm the code contract, not superiority.
- **External U.S. infrastructure validation is prepared but not conducted (PR #52).** The sector-independent operator-study protocol and fail-closed evidence manifest check demand real operator permission, independent assessor evidence, matched service baselines, and actual exposure, downtime, legitimate-request failure and false-assurance counts. Structural completeness cannot authenticate a real operator or prove impact.
- **Authority-outage action inference remains limited.** PRs #43–#50 established physical outage witnesses, four action interventions, real timed observations, conservative UNKNOWN intervals, draft six-family feasibility registration and sample-size caution. The complete six-family physical study is not authorized/frozen; no field critical-infrastructure resilience improvement has been quantified.
- **Research claims must remain separated.** Software CI success, completed exploratory laboratory actions, a positive held-out laboratory comparator result (if eventually observed), and independent operator field impact are four different evidence levels. Neither GitHub traffic nor self-reported records can bridge those levels.

 Research pre-alpha. A merged implementation or passing CI proves only the documented local or CI behavior, not superior AI performance, commercial adoption or critical-infrastructure field validation.

| Post-fix safety verification ("did the fix actually work, safely") | `remediation_verification.py` requires four assertions to each independently reach VERIFIED before a remediation is accepted, not just the vulnerability-resolved check that existed before: vulnerability resolved, no regression, no new known vulnerability in the version moved to, dependency resolution succeeds. All four are now piloted against real targets, not just fixtures, in two places: `experiment-b/mechanism-lab/verify_remediation.py` runs `mvn dependency:resolve` and `mvn test` for real against the actual Maven project built in CI (no regression, dependency resolution); `experiment-b/real-cve-remediation/verify_remediation.py` runs all four together against the one real, independently-probed CVE fix this repository already has (CVE-2020-8203, lodash 4.17.11 to 4.17.21 via real `npm install`): the existing behavior probe for vulnerability-resolved, a real `npm install --dry-run` for dependency resolution, the probe piped through a real exit-code check for regression, and a scan against two real published advisories (version ranges confirmed against OSV.dev, not guessed) for no-new-known-vulnerability. Negative-control checked: scanning the pre-fix version against those same advisories correctly flags it, confirming the scan discriminates rather than passing everything. The registration step itself is now generalized: `remediation_target.py` reads a declarative JSON schema (resolver command, test command, package/new-version/advisories) instead of requiring a new hand-written script per project, and `experiment-b/real-cve-remediation/verify_remediation_via_registration.py` re-runs the real lodash pilot through this generic path, reaching the identical `accepted: True` / all-four-VERIFIED result as the original hand-written `verify_remediation.py`, proving the generalization is load-bearing rather than cosmetic. 10 unit tests for `remediation_target.py` pass | The `vulnerability_resolved` assertion is deliberately excluded from what the registration mechanism automates: it still requires a human to supply Evidence from a separately reviewed, CVE-specific probe, by design, so an operator cannot yet point this at an arbitrary project and get a fully automated verdict; only the one lodash target has actually been re-registered through the generic path so far, not a third, independent project; the advisory list for the CVE pilot is two hand-picked, hand-verified entries, not a live lookup against a real advisory feed |
| Intrusion-informed containment (authorized detections as a new input) | `detection_intake.py` admits a detection alert only from a pre-registered, trusted source, following the same fail-closed registered-source pattern as `exploit_confirmation.py`; rejects unregistered sources, malformed alerts, future-dated or stale signals outright; feeds an admitted detection into the existing `assessment.assess()` pipeline as one independent evidence source and reuses the existing re-verification scheduler (marks the subject changed, raises its risk floor) rather than building a second one. The scheduler update takes the `AdmissionResult` `admit()` returns, not a raw detection, and raises `TypeError` on anything else, so a detection that skipped admission cannot reach the scheduler by construction. 15 unit tests pass; this consumes detections produced elsewhere and does not generate detection rules, which is a different, unbuilt capability | Not wired into any CI workflow, the main pipeline, or a real EDR/SIEM feed yet; unit-tested against fixtures only; does not yet tighten the action gate's response deadlines or approval tier based on detection confidence, which the design doc also flags as still open for this extension; the registered-source check is a policy check against a claimed `source_id`, not an authentication check, so provenance is not yet cryptographically or transport-level verified the way `exploit_confirmation.py` verifies a signature by probing the authorized host live |
| Source-code fix verification (SAST findings as a new evidence source) | `sast_findings.py` implements the Section 7.1 design sketch's four-assertion composite for a source-code finding: the finding is confirmed present at a scanner-stable fingerprint before the fix, confirmed absent at the same fingerprint after, no regression (reusing `regression_check.py` rather than a second mechanism), and no new high-or-critical finding introduced in the touched files, all admitted only from an operator-registered, version-pinned scanner via the same fail-closed registration pattern as `detection_intake.py`. `evaluate_fix()` mirrors `remediation_verification.evaluate()`'s all-four-or-nothing rule exactly. Now piloted against a real scanner, not only fixtures: `experiment-b/real-sast-pilot/` runs a real `semgrep` subprocess (pinned to a repo-local rule file rather than the live registry, so the scan stays reproducible without a network dependency) against a real SQL-injection fixture, applies a real fix in place, and runs a real sqlite3-backed regression check; all four assertions reach VERIFIED. The pilot's own build surfaced and fixed two real bugs along the way: `confirm_no_new_high_severity`'s severity check was comparing Semgrep's actual `ERROR`/`WARNING`/`INFO` vocabulary against a `"high"`/`"critical"` string match that could never be true (a silently vacuous check), fixed with an explicit severity map; and the before/after scans were originally run against two separately named fixture files, which (since the fingerprint includes the file's own name) made the "same fingerprint, now resolved" check meaningless by construction, fixed by scanning both states at one shared disposable path to simulate a real in-place edit. 23 unit tests for the core module plus 13 for the pilot pass, and the pilot runs in its own CI workflow (`real-sast-pilot.yml`) | The pilot is one hand-registered fixture, not a mechanism an operator can point at an arbitrary codebase; no real scanner integration exists for a production repository; the design sketch's optional dynamic check for externally reachable findings is not implemented; reachability-based prioritization using the dependency graph in place of CVE/EPSS scoring is not implemented; not wired into the main pipeline, only its own CI workflow; the pilot's finding identity is a locally computed stand-in (rule, file, enclosing function via AST), not Semgrep's own native fingerprint, which requires a logged-in Semgrep Cloud Platform session this pipeline deliberately avoids |

## Scientific reporting rules

Use precise denominators and versioned sources, distinguish physical observation from plan generation, and do not treat passing unit tests as outcome validation. Preserve negative results and report calibrated uncertainty, temporal leakage checks, action eligibility, and independent verification boundaries. A positive AI decision-value claim requires the preregistered comparator, relative threshold, and confidence interval on independent configuration groups. Do not start the 1,200-trial campaign until the revised protocol and mechanical pilot are formally frozen.
