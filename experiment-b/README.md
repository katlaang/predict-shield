# Experiment B: inconsistent access-control enforcement

**Status: experimental source and fixtures, not yet a validated integrated experiment.**

This self-contained localhost-only laboratory uses two instances of the same Java 25 / Spring Boot application with different initial authorization states:
- service-a at 127.0.0.1:18081 starts correct: HTTP 403 for a revoked operation.
- service-b at 127.0.0.1:18082 intentionally starts stale: HTTP 200 for that same operation.
- The independent Python probe detects mismatched enforcement. It may request a lab-only revocation after explicit opt-in, and probes both endpoints again independently of any action acknowledgment.

There is no real principal identity, event bus, propagation delay, simulated partitions, or runtime policy authority yet. This is a first-stage control-drift fixture, not a production security system. The lab is unsuitable for deployment beyond localhost.

## Prerequisites
Docker Engine with Docker Compose, with support for building Java 25 images; Python 3.10+.

## Run
From `experiment-b`:

```bash
export LAB_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
docker compose up --build -d
python run.py --output b-readonly.json
python run.py --correct-lab --output b-corrected.json
docker compose down
```

The initial read-only run should classify the stale authorization state as NOT VERIFIED. The opt-in lab correction should request revocation only from a service returning HTTP 200, then independently probe again. A failed correction is not accepted as proof.

## Unit tests
```bash
python -m unittest discover -s experiment-b -p "test_*.py" -v
```
Tests are mock-transport unit tests and do not prove the Java lab compiles or runs. Integration test evidence must be recorded separately.

## Controls and limitations
- Define both services' expected denial behavior before running tests. See `fixtures/expected-policy.json`.
- Keep the disposable lab token private. The token gates the **lab mutation endpoint**, not an enterprise authorization control.
- All services bind to the loopback interface; do not expose this intentionally flawed testbed.
- Reports include observations, action attempts, and post-action observations. They are *not* cryptographically authenticated.
- The next checkpoint must add real fault injection, explicit policy evaluation, audit persistence, repeated test runs, and service-disruption measurements.


## v2.2 reproducible AI training-data extension

The development branch adds reproducible trial plans, a bounded resettable
Java fixture, an opt-in HTTP measurement collector, and an initial ML training
and evaluation script.

### Experiment design

The manifest contains **100 configuration groups**, divided into **60 train,
20 calibration, and 20 held-out test groups**. Each configuration has four
candidate actions (resync_policy, restart_enforcer, gateway_restrict,
monitor_only) and three independently seeded repeats: **1,200 planned replays**.
No actual actions, outcome labels, or model predictions are generated by the
manifest. Actions and repeats from the same configuration never cross splits.

Fault scenarios vary logical enforcement-point count, cache TTL, propagation
delay, intended traffic, dependency depth and redundancy. These are lab
parameters, not measured real-world frequency distributions. The fixture
implements a subset of the declared fault effects; an event bus, separate
enforcement processes, and full network fault behavior do not yet exist.

### Build and execute a small pilot

Run from the experiment-b directory. Create two distinct disposable secrets:

~~~bash
export LAB_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
export LAB_ORACLE_TOKEN="$(python -c 'import secrets;print(secrets.token_urlsafe(32))')"
docker compose up --build -d
python generate_manifest.py --out generated --seed 20261110
python collect_training_data.py --execute-lab --manifest generated --out results --limit 4
~~~

After checking the four-action pilot and the environment, an explicitly
requested full collection uses the same collector with --limit 1200.
Use --offset to continue from a later trial after a failure; completed
records are never overwritten. Stop the lab with docker compose down.

### Separate records and access

| Directory | Content | Trust / use |
| --- | --- | --- |
| results/pre_action/ | Pre-action condition and external probe observations | Candidate model features |
| results/verification/ | Post-action probe outcomes and scope caveats | Verification analysis, not oracle |
| results/operations/ | Actual serial HTTP request failures and latency | Measured outcome label |
| results/oracle/ | Token-protected internal Java fixture truth | Evaluation labels only; mode 0600 |

The laboratory oracle and targets currently run in the same process. The
token and storage boundaries reduce accidental leakage but do not provide
independently operated production-grade ground truth. The intended traffic_rps
setting is not yet an enforced load; the collector explicitly records actual
request rate for its 40 HTTP workload requests. Because only declared target
scope is checked, a successful deny probe does not prove complete inventory
reconciliation and the normal verifier does not claim full-scope VERIFIED.

Raw experiment outputs and oracle labels are gitignored. Keep the oracle
data outside model-feature preparation and never commit private credentials.

### Train the first AI action-outcome estimator

Only after all executed and matched records exist:

~~~bash
python -m pip install -r requirements-ml.txt
python train_action_model.py --data results --out reports/model-evaluation.json
~~~

Training will refuse missing records, duplicate run IDs, mismatched groups,
or leaked train/calibration/test partitions. The prototype fits models for
residual exposure and legitimate-traffic failures and evaluates on held-out
configurations.
Its intervals use split-conformal calibration, with marginal rather than
per-service safety guarantees. These are **lab fixture outcomes**, not proof
of model benefit in a real network.

### Tests

GitHub CI additionally builds Java 25 / Spring Boot with Docker, exercises
the original smoke test, and executes the first four paired laboratory

controllers are also documented.

**Still absent:** trained-model integration into the decision engine,
physically separate oracle, independent inventory reconciliation, real

and external adoption/validation.
