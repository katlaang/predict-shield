# PREDICT-SHIELD: authorized real-network pilot

This is a **new field-network experiment**, not a reproduction of the DVWA v3 fused web detector or a claim of critical-infrastructure effectiveness. It is designed for a **real home, business or ISP network you own or have written permission to monitor**. The deployment is passive and **monitor-only**: it reads Zeek JSON connection logs generated by an operator-provisioned network sensor. No discovery scans, packet injection, active probes, firewall changes, route changes, quarantine or automatic mitigation are performed.

## What this actually tests

- Can a passive network sensor observe real connections and supply structured flow telemetry to PREDICT-SHIELD?
- Can a newly fitted **unsupervised Isolation Forest** model on that site's time-separated flow history emit anomaly scores on later traffic?
- What are observed anomaly events per 1,000 flows, missing-input fractions and coverage, when the model and threshold are **frozen**?
- Does the read-only local dashboard show the live aggregate state without revealing raw IP addresses or URLs?

It does **not** measure attack recall, verified false-positive rate, AI decision superiority, multi-site generalization, production resilience or the complete AI threat-remediation pipeline. All alerts remain **unverified anomalies** until independently reviewed.

## Network prerequisites and safety

1. Use a **Linux** sensor device on a network you own or that an operator has explicitly authorized. For example, a spare computer or a Linux VM with an interface receiving copies of traffic from an approved switch mirror/SPAN port or a network TAP. On a regular switched port you may only observe that sensor's own traffic, not the entire LAN. Verify the sensor interface receives appropriate coverage without reconfiguring live customer network elements.
2. Install a supported Zeek network monitor using its official installation documentation: https://docs.zeek.org/en/current/ . Configure JSON output using `LogAscii::use_json=T` or the Zeek `policy/tuning/json-logs.zeek` policy. Zeek's `conn.log` provides timestamps, protocol, duration, byte/packet counts and connection state. Some values are optional.
3. Use a restricted directory for **raw** Zeek logs and locally trained models. Restrict read permissions and retention; IP addresses, client identifiers and possibly sensitive service metadata exist in the **source** logs even though this tool does not publish them. Do not commit raw telemetry, model files, complete consent records, or identifying site details to this public repository.
4. Get a written scope/permission, capture-interface identification, retention plan and escalation contact. Start with monitoring only; perform no active attacks or production changes. If the network is critical infrastructure, work with the responsible operator's security/change authority before any next phase.

### Setup

From a clone of `katlaang/predict-shield` on the sensor:

```bash
python3 -m venv .venv
. .venv/bin/activate
python -m pip install 'numpy==2.3.4' 'scikit-learn==1.7.2'
```

Run Zeek with capture permissions on an interface **you are authorized to monitor**. Replace `SENSOR_INTERFACE` with the actual name of the approved capture port, and start it from a restricted working directory:

```bash
# Example only. Zeek requires appropriate packet-capture permissions.
mkdir -p /secure/predict-shield/zeek
cd /secure/predict-shield/zeek
zeek -i SENSOR_INTERFACE LogAscii::use_json=T
```

The command above runs continuously until stopped. It cannot run without capture permissions and a valid interface. Zeek is a separate sensor; this Python pilot does not invoke it or request elevated permissions. Validate the actual `conn.log` is JSON, **not the default TSV**, before continuing. Zeek logs can also be collected by an existing independently approved collector.

### Three genuinely distinct time periods

Collect **separate** Zeek JSON connection logs in chronological order:

- Baseline: at least **200** scorable flows in an initial period, ideally representing ordinary operation. These flows are **assumed** normal; that assumption is not verified by a label.
- Calibration: at least **100** scorable flows from a **later non-overlapping** period. It sets a provisional **0.5% calibration alert budget**.
- Evaluation: fresh, later real-network flows which were **not** in either training or calibration. These can be processed from a completed log file or in live `watch` mode.

The minimum counts only make software operation feasible; a defensible deployment needs substantially longer representative windows, workloads, peak/off-peak cycles, independent ground-truth review and operator-approved evaluation criteria. Baseline contamination by actual attacks can make an unsupervised detector learn malicious behavior as normal.

Save completed logs as three **private** files. Then from the repository root:

```bash
python experiment-b/field-network/pilot.py fit \
  --site authorized_lab_01 --operator-authorized \
  --baseline /secure/predict-shield/baseline-conn.json \
  --calibration /secure/predict-shield/calibration-conn.json \
  --out-dir /secure/predict-shield/model-01

python experiment-b/field-network/pilot.py evaluate \
  --site authorized_lab_01 --operator-authorized \
  --input /secure/predict-shield/evaluation-conn.json \
  --model-dir /secure/predict-shield/model-01 \
  --output /secure/predict-shield/evaluation-summary.json
```

Training freezes the model, threshold, exact local implementation SHA-256, model SHA-256, input hashes, model library version and site pseudonym. The evaluator fails if the source is reused or overlaps the calibration timestamps, if the model/code changed, or if a report already exists. It publishes **counts and source hashes only**, no raw flows. Existing reports are never silently overwritten.

### Monitor ongoing real traffic with a local dashboard

Start with a running Zeek instance that writes JSON `conn.log`. The watcher starts **at the end of the existing file** and counts only new complete lines, handles common log rotation and terminates after a bounded duration (or Ctrl+C):

```bash
python experiment-b/field-network/pilot.py watch \
  --site authorized_lab_01 --operator-authorized \
  --input /secure/predict-shield/zeek/conn.log \
  --model-dir /secure/predict-shield/model-01 \
  --duration-seconds 3600 \
  --dashboard-port 8767 \
  --output /secure/predict-shield/live-aggregate.json
```

Open **http://127.0.0.1:8767/** on that same machine. The read-only dashboard binds only to loopback and shows flow counts, aggregate anomalies, incomplete records and the frozen model. Nothing is sent to Vercel, GitHub, the public network or a remote dashboard. The watcher never runs in background without the operator starting it.

### Security limits and evidence protocol

- **No automated response**. The model only assigns unsupervised anomaly scores; it does not know whether the event is malicious. On a production site, no route/firewall/endpoint modification is permitted based on this signal.
- **No unattended claims of accuracy**. Without independently adjudicated known-benign and known-malicious flows, `false_positive_rate` and `attack_detection_recall` remain `null`. A 0.5% calibration threshold is **not** a verified future false-positive guarantee.
- **No known independent field pilot has yet run** as of this code checkpoint. CI generates deterministic **synthetic** Zeek flow fixtures for engineering unit tests only. Its success is not field evidence.
- **Data quality**: optional Zeek byte/packet fields may be absent. The model records missingness features and counts malformed/incomplete records rather than pretending they are real benign zero-byte connections.
- **Privacy**: do not upload raw connection records or sensor-trained model files to public GitHub or Vercel. The live dashboard is private and only displays aggregate counts.
- **Evaluation**: include an independent analyst's alert review, a rule-only baseline, AI/no-AI ablation, operational impact, disjoint collection windows, and at least one separate network before claiming generalization or decision-value improvement.

Official protocol fields: https://docs.zeek.org/en/current/reference/logs/conn.html and https://docs.zeek.org/en/current/tutorial/logs.html
